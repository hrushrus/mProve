App design · Phase 1 MVP · from spec V3

mProve: the deck-to-athlete feedback loop

Coaches speak a few seconds of feedback during practice. The app turns each note into a row in the team's Google Sheet. Once a week, AI drafts a check-in per athlete for the coach to approve. Athletes reply and keep a training journal, and both feed next week's check-in.

Swimming first, multi-sport schema 1 coach · 8–12 pilot athletes mProve Master Database V2 Coach approves every send
The three modules

One loop, three people talking

Coach → Athlete

Deck notes & weekly check-in

  • Tap-to-record, 3–8 second voice notes
  • One clip can name several athletes; each gets its own row
  • Weekly AI draft, 140–180 words, three parts
  • Coach edits and taps Approve & Send All
Athlete → Coach

Replies on a specific cue

  • Reply to a whole check-in or to one observation
  • Coach inbox grouped by athlete and squad
  • Close a thread in-app or mark it "addressed at practice"
Athlete → Self

Journal & metrics

  • RPE and feel sliders, energy, sleep, focus
  • Splits, stroke counts, underwater kicks against a target
  • Private or shared with coach; only shared entries reach the AI
Eyes stay on the poolRecording is one tap with no typing on deck. Fixing names and details waits until after practice.
Nothing goes out unseenAI writes drafts only. Every check-in needs the coach's approval before it is sent.
The Sheet is the recordEvery note, check-in, reply and journal entry is a row a coach can open, read and edit.
Works without signalNotes and journal entries queue on the phone and upload when it reconnects.

User flows

How a note travels

Capture a deck note

  1. Coach holds the button and says "Chris had strong turns; Drew dropped his elbow on the turn."
  2. The phone saves the audio and the session tag, then vibrates. If offline, the note waits in the queue.
  3. On upload, the backend saves the clip to Drive and sends it to Gemini with the roster and swim vocabulary.
  4. Gemini returns one object per athlete mentioned. Each one becomes a row in Coach_Feedback_Log.
  5. Rows with an unsure name go to the Review screen (C2). The rest are ready.
If no athlete is recognised, the row is saved with a blank Athlete_ID and flagged, so the note is never dropped.

Weekly check-in

  1. Sunday 18:00, a scheduled script (or the coach's menu button) collects the last 7 days of rows for each athlete.
  2. It includes confirmed deck notes, Q&A threads, and journal rows marked Coach_Shared.
  3. Gemini drafts a 140–180 word check-in using the spec's prompt. The draft goes to Weekly_Digests as Pending Review.
  4. Coach reviews in C4 or directly in the Sheet, edits, and approves.
  5. Approve & Send All emails each athlete (parent on CC), shows it in the app, and marks the row Sent.
An athlete with fewer than 2 notes and no journal entries gets no draft. They show up as "Not enough data" for the coach.

Athlete asks a question

  1. Athlete opens a note or check-in and taps Reply.
  2. A row is added to Athlete_Coach_Threads with Sender_Role = Athlete and status Unread.
  3. The coach's Inbox badge goes up. The question also appears on the On deck screen before the next practice.
  4. Coach replies (Replied_in_App) or answers in person (Addressed_at_Practice).
  5. The exchange is included in that week's check-in.

Athlete logs a practice

  1. After practice, a reminder (sent 30 minutes after the session ends) opens the Journal screen.
  2. Athlete sets RPE and feel, adds a metric against a target, and dictates a sentence.
  3. The entry saves on the phone and uploads to Athlete_Self_Journal.
  4. Shared entries appear on the athlete's coach view and feed the weekly draft. Private ones stay with the athlete.

One change to the layout firstStacked tables → five tabs

Right now all five tables are stacked in one sheet, with the table name in column A and a header row above each block. That reads well, but the app can't add rows safely: a new deck note belongs in the middle of the sheet, and inserting it there shifts every table below. Each table needs its own tab with the header in row 1, so new rows simply go at the bottom.

The header rows also show #ERROR! in column A. That usually means the cell's text starts with =, + or -, so Sheets reads it as a formula. Moving to separate tabs removes those cells.

The column names stay as you have them. The split is a copy-and-paste, and I'd keep your current sheet as an archive tab.

Parsing contract

The audio goes to Gemini together with the squad roster (names and aliases) and the sport's lists of events and focus areas. Gemini must return a JSON array that matches this shape, or the request is retried once and then saved as a single flagged row.

The spec's example clip ("Chris had strong turns; Drew dropped his elbow on the turn; Alex had great momentum") returns three objects, which become three rows sharing one Clip_ID.

Stack choice

Option A, Option B, or a mix

A · Weekend build

iOS Shortcut to Drive, Google Forms or AppSheet for athletes, Apps Script menu buttons.

  • Running at practice within days
  • No offline queue, no coverage strip, no inbox
  • Athletes use separate forms, so replies don't sit next to the check-in

A+ · Recommended for Phase 1

Option A's Google backend, with the one web app designed above in front of it.

  • Delivers screens C1–C4 and A1–A3 as designed
  • Free to run at pilot size, apart from small Gemini costs
  • About 2 weeks to build, which fits the spec's Phase 1 window
  • The Sheet stays the record, so moving to Option B later doesn't lose data

B · Club scale

React Native or Flutter, a FastAPI or Cloud Function backend, Firebase or Supabase synced to Sheets.

  • Native Bluetooth mic control and push notifications
  • Handles many squads and season-long analytics
  • Several weeks of work, and app store review. Better after the Phase 2 pilot shows what coaches actually use
Before building

Things to settle

Minors' data and consentMost pilot athletes are under 18 and some are under 13. Get parental consent before recording names in voice notes, and set how long audio is kept (30 days is suggested).
Athletes can't open the SheetSharing the Sheet would let every athlete read every other athlete's notes. Athletes only see their data through the app, and the backend filters rows by the signed-in email.
Email sending limitsApps Script on a personal Gmail account can email about 100 recipients a day. A Google Workspace account allows about 1,500. A 12-athlete pilot with parents on CC is around 24, which is fine. Sending for a whole club would need Workspace or Option B.
Two notes saved at onceTwo uploads arriving together could write to the same row. The backend locks the Sheet briefly for each write.
Deck noiseWhistles, echo and splashing will hurt accuracy. Phase 2 tests the phone's built-in mic against a clip-on mic. Name matching is the part to measure most closely.
Which Google accountThe Sheet, Drive folder and script need one owner, ideally a club account rather than a coach's personal one, so the data stays with the club.

What gets built, in order

  • Create the five tabs with columns, dropdowns and protected headers
  • Load a sample roster with aliases
  • Swim lists for events and focus areas

Days 3–5 · Voice to row

  • Apps Script upload endpoint
  • Gemini parsing with the roster prompt
  • Split by athlete, flag unsure names
  • Test on 20 recorded sample clips

Days 6–8 · Coach screens

  • C1 capture with offline queue
  • C2 review, C3 inbox and coverage
  • Watch / Shortcut capture

Days 9–11 · Weekly check-in

  • Draft generation from all three sources
  • C4 review and Approve & Send All
  • Gmail delivery and write-back

Days 12–14 · Athlete screens

  • A1 check-ins and replies
  • A2 journal, A3 progress
  • Sign-in by email, own rows only

The spec puts athlete screens in Phase 3. Since they use the same app and the same backend, I'd build them now but keep them turned off for the Phase 2 deck tests.
